## Problem Statement

Every new project requires manually orchestrating a 3-phase AI development workflow: Design & Research (turning a raw idea into scoped Linear issues), Bootstrapping (CLAUDE.md, AGENTS.md, git workflow, Linear integration), and Development (Sonnet implementation, adversarial review, fix loop, Opus final review, issue closure). The prompts are written from scratch each time, the issue structure varies, and the review loop lacks standardization. This wastes time and produces inconsistent quality.

The builder has validated this workflow on forkcast-cli and wants to codify it into reusable Claude Code skills with standardized prompts.

## Demand Evidence

The builder IS the user. They've run this workflow manually across projects (primarily forkcast-cli) and identified specific pain points:
- Writing implementation prompts from scratch per issue
- Manually routing between models (Sonnet for impl, adversarial review, Opus for final)
- No quality gate on Linear issues before implementation begins
- Manual Linear state transitions (Backlog → Todo → In Progress → In Review → Done)
- Manually creating CLAUDE.md from templates and running /init each time

## Status Quo

Current workaround: Write a detailed Linear project description with the workflow vision, manually invoke gstack skills (/office-hours, /plan-eng-review) for design, copy-paste a CLAUDE.md template from forkcast-cli, manually create Linear issues with varying quality, then run Sonnet implementation → adversarial review → fix → Opus review as separate Claude Code sessions with hand-written prompts. Linear state transitions are manual.

The forkcast-cli CLAUDE.md (194 lines) represents the current gold standard template with:
- Git workflow (main/dev branches, worktrees, branch naming)
- Linear workflow (state machine with explicit state IDs)
- Issue dependency tracking
- Build commands and architecture docs

## Target User & Narrowest Wedge

**Target user:** Solo developer or small team using Claude Code + gstack + Linear for AI-assisted development. They have a working but ad-hoc workflow and want to standardize it.

**Narrowest wedge:** A `harness-dev` skill that takes a Linear issue ID, validates it has required sections, runs Sonnet implementation in a worktree, runs adversarial review, routes fixes, runs Opus final review, and closes the issue with Linear state transitions. This is the repeating loop — one issue at a time.

## Constraints

- Must be Claude Code skills (SKILL.md format), not a separate runtime
- Must integrate with Linear MCP for issue reading/writing and state transitions
- Must integrate with gstack ecosystem (leverage /adversarial-review, /codex, etc.)
- Must work across different project types (TypeScript, Python, etc.) — language-agnostic
- Issue schema must be shared across all three skills
- Each skill must be independently invocable

### Model Routing Constraint (PREREQUISITE — must resolve before build)

Claude Code skills cannot directly specify which model to use for sub-invocations. This is a fundamental constraint that shapes the entire design. The resolution:

**The skill does NOT switch models itself.** Instead, the skill is designed as a human-in-the-loop orchestrator that:
1. Runs in whatever model the user invoked it with (recommended: Sonnet for cost)
2. Performs implementation directly (no model switch needed — the skill IS the implementation agent)
3. Invokes /adversarial-review:run which handles its own multi-model routing internally
4. For the Opus final review step: the skill outputs a structured review prompt and instructs the user to switch to Opus (or dispatches a subagent if the Agent tool supports model hints)

**Fallback:** If subagent model hints are not supported, the skill pauses at the Opus review step and says: "Implementation and adversarial review complete. Switch to Opus 4.6 and run `/harness-review WHI-123` for final review." This makes the Opus step a separate, tiny skill rather than an inline model switch.

This constraint is resolved. The design proceeds with this approach.

## Premises

1. Phase 1 (Design → Structured Linear Issues) and Phase 3 (Dev Loop) are co-dependent. The issue schema that bridges them is the shared contract. Build them together.
2. Deliverable is Claude Code skills (SKILL.md files) leveraging gstack and Linear MCP for orchestration.
3. Quality of implementation depends on Linear issue description quality. The issue description is the PRIMARY context source; CLAUDE.md provides supplementary project-level context (build commands, git workflow, architecture overview). The issue must be implementable with only these two sources — no external context, no asking the user for clarification.
4. Three phases are sequential but each skill is independently invocable.
5. Model routing (Sonnet for implementation, adversarial review, Opus for final review) is core value.
6. (Revised from subagent challenge) An issue quality gate before implementation starts is required — the dev loop skill must refuse to start if the issue lacks required sections.

Three independent skills sharing a common Linear issue schema:
- `/harness-design`: Idea → scoped Linear project with milestones + issues in required schema
- `/harness-bootstrap`: CLAUDE.md + AGENTS.md + git setup from template
- `/harness-dev`: Issue quality gate → Sonnet impl → adversarial review → fix → Opus review → close

Effort: M (CC: ~2-3 hours total)
Risk: Low
Pros: Each skill focused and testable, composable with gstack, independently invocable

One skill `/harness` running the full pipeline from idea to closed issue.
Effort: L (CC: ~3-4 hours)

### Approach C: Template-Only

Effort: S (CC: ~1 hour)
Risk: Low
Pros: Fastest to ship, no new code
Cons: Still requires manual orchestration, workflow not truly encoded

## Recommended Approach

**Approach A: Three Focused Skills + Shared Schema.**

The shared issue schema is the linchpin. It defines what a "well-formed issue" looks like, and both the design skill (which creates issues) and the dev skill (which validates and implements them) operate on it. Linear is the state store. The schema bridges the phases without coupling the skills.

## The Shared Issue Schema

Every Linear issue created by `/harness-design` and validated by `/harness-dev` must contain these sections in its description:

```markdown
## Context
[What this issue is about, why it matters, how it fits into the project]

## Acceptance Criteria
- [ ] [Specific, testable criterion]
- [ ] [Specific, testable criterion]

## Architecture Notes
[Key technical decisions, patterns to follow, files to modify]
[Reference to CLAUDE.md architecture section if applicable]

## Dependencies
[Which issues must be done first, what external resources are needed]

## Scope Boundary
[What is explicitly NOT in scope for this issue]
```

The dev skill's quality gate checks for these sections before proceeding.

## Skill 1: `/harness-design`

**Purpose:** Transform a raw idea (from a Linear project description or conversation) into a fully scoped Linear project with milestones, phases, and issues in the required schema.

**Input:** Linear project ID or name, or a free-form idea description

**Workflow:**
1. Read the Linear project description (or take a free-form input)
2. Run /office-hours interactively to refine scope and produce a design doc. NOTE: /office-hours is an interactive skill that asks the user questions. This is intentional — harness-design is NOT an automated pipeline. It's a guided session where the user participates in scoping. The design doc output is saved to `~/.gstack/projects/{slug}/`.
3. Run /plan-eng-review interactively for architecture decisions. Again, user participates.
4. Read the design doc and architecture review outputs. Extract: project structure, feature list, technical decisions, data flow, API contracts.
5. Decompose into milestones → phases → issues. Each milestone maps to a Linear milestone. Each phase is a group of related issues. Issues are ordered by dependency.
6. For each issue, write the description in the shared schema format (see schema section above). The Context section must reference specific sections of the design doc. The Architecture Notes section must reference specific decisions from the eng review.
7. Create all issues in Linear with proper dependencies (blocks/blockedBy)

**Data flow:** Design doc (markdown) + Eng review output → skill parses these → generates structured issue descriptions → creates in Linear. The skill's core logic is the translation from free-form design doc to structured issue schema.

**Output:** Linear project populated with structured issues, milestones, and dependency chain

**Key requirement:** Each issue description must be detailed enough that an LLM can implement it with only the issue description + CLAUDE.md. This means:
- Concrete file paths and function signatures where applicable
- Specific error handling expectations
- Test requirements
- Edge cases to handle

## Skill 2: `/harness-bootstrap`

**Purpose:** Set up a new project's development environment with CLAUDE.md, AGENTS.md, git workflow, and Linear integration.

**Input:** Linear project ID, git remote URL (optional)

**Workflow:**
1. Read the Linear project details (team, issues, milestones)
2. Detect existing repo state:
   - If `.git` exists: use existing repo, skip git init
   - If `.git` does not exist: initialize with `git init`, create main + dev branches
   - If remote URL provided: add remote and push
3. Detect technology stack from existing files (package.json → Node/TS, pyproject.toml → Python, go.mod → Go, Cargo.toml → Rust). If no files exist, ask user: "What's your tech stack? [TypeScript / Python / Go / Rust / Other]". For "Other", generate a minimal CLAUDE.md with only the project-agnostic sections (git workflow, Linear workflow, worktree lifecycle).
4. Generate CLAUDE.md from template with:
   - Project overview (from Linear project description)
   - Git workflow (main/dev branches, worktree lifecycle, branch naming with Linear issue IDs)
   - Linear workflow: query the team's states via Linear MCP (`list_issue_statuses`), embed a name→ID mapping table in CLAUDE.md. Harness-dev uses state NAMES for transitions (resolved to IDs at runtime via MCP), not hardcoded IDs. This ensures the workflow survives if the team changes their state configuration.
   - Issue dependency chain (from Linear)
   - Build & development commands (from detected stack)
   - Architecture section (from design doc if available in `~/.gstack/projects/{slug}/`)
5. Generate AGENTS.md with content: `# AGENTS.md\n\nSee [CLAUDE.md](./CLAUDE.md) for project context, development workflow, and coding standards. Follow all instructions in CLAUDE.md when working on this project.`
6. If `~/.gstack/config.json` does not exist, create it with defaults: `{"review_mode": "adversarial-review"}`
7. Commit CLAUDE.md and AGENTS.md

**Output:** Repository bootstrapped with CLAUDE.md, AGENTS.md, proper git structure

**Template source:** Abstract the generic parts of forkcast-cli's CLAUDE.md (git workflow, Linear workflow, worktree lifecycle, task transition) into a reusable template. Project-specific sections (architecture, commands, domain knowledge) get filled in per-project.

## Skill 3: `/harness-dev`

**Purpose:** Implement a single Linear issue through the full dev loop with review and Linear state transitions.

**Input:** Linear issue ID (e.g., WHI-123)

**Workflow:**

### Step 1: Issue Quality Gate
- Read the Linear issue via MCP
- Validate required schema sections exist by checking for markdown headers: `## Context`, `## Acceptance Criteria`, `## Architecture Notes`, `## Dependencies`, `## Scope Boundary`. Validation is markdown header pattern matching (regex: `^## (Context|Acceptance Criteria|Architecture Notes|Dependencies|Scope Boundary)`). Each section must have at least 20 characters of non-whitespace content below the header (excludes template placeholder text like `[What this issue is about...]`).
- Check that CLAUDE.md exists in the repo root. If not, warn: "No CLAUDE.md found. Worktree defaults to `.worktrees/`, dev branch defaults to `dev`. Consider running `/harness-bootstrap` first." Proceed with defaults.
- Check that blocked-by issues (from Linear relations) are all in "Done" state
- If validation fails: output a checklist showing which sections are present (checkmark) and which are missing (X), with a one-line description of what each section should contain. STOP. Do not proceed.
- If validation passes: proceed

### Step 2: Setup
- Move Linear issue to "In Progress" via MCP state transition (Backlog/Todo → In Progress)
- If the issue has sub-issues, move those to "In Progress" as well
- Read CLAUDE.md to get the worktree naming convention and dev branch name
- Create a git worktree: `.worktrees/<name>` branched from `dev`
- Branch naming: `<type>/WHI-<N>-<short-desc>` (type inferred from issue title or label: feat/fix/chore)

### Step 3: Implementation
- Read the issue description as the implementation spec
- Read CLAUDE.md for project-level context (build commands, architecture, conventions)
- Implement the feature/fix per acceptance criteria
- Run build commands to verify compilation
- Run tests if they exist
- Commit changes on the feature branch

### Step 4: Adversarial Review
- **Default:** Invoke /adversarial-review:run on the changes (this skill handles its own multi-model routing)
- **Alternative:** If the user has configured `review_mode: codex` in the skill config, invoke /codex:rescue instead
- Configuration: the skill reads a `review_mode` field from `~/.gstack/config.json` (default: "adversarial-review")
- Collect review findings. Classify each finding by severity:
  - **Critical/High:** Must be fixed before proceeding
  - **Medium:** Should be fixed, but won't block
  - **Low/Style:** Logged but not auto-fixed (prevents over-correction bias)

### Step 5: Fix Loop
- If Critical/High findings exist:
  - Assemble the fix context bundle: (1) original issue description, (2) current git diff, (3) review findings with severity
  - Fix the Critical/High issues in the current worktree
  - Re-run build and tests to verify fixes don't break anything
  - Re-run adversarial review on the accumulated diff (full diff from dev to current HEAD). Note: `/adversarial-review:run` operates on the working tree diff, not a specific commit range. The re-review covers all changes including fixes, which is acceptable — the review will confirm the fixes resolved the issues and not flag already-addressed items.
  - **Known limitation:** The adversarial review skill is stateless and may re-flag issues that were already fixed. To mitigate: after collecting re-review findings, harness-dev compares them against the prior round's findings (by file path + description similarity). Findings that match a previously-resolved item are auto-suppressed. If deduplication is imperfect, the 2-iteration cap prevents infinite loops — and any remaining items get flagged for human review rather than burning more cycles.
  - Maximum 2 fix iterations total. One iteration = one fix pass + one re-review.
  - If Critical/High issues persist after 2 iterations: move issue to "In Review", add a Linear comment listing unresolved findings, and STOP. Flag for human review.
- If no Critical/High findings: proceed to Step 6

### Step 6: Final Review Handoff
- The skill cannot switch to Opus mid-execution. Instead:
  - Move Linear issue to "In Review"
  - Add a Linear comment with: implementation summary, review findings addressed, remaining Medium/Low items
  - Output to the user: "WHI-xxx implementation and adversarial review complete. For Opus final review, switch to Opus 4.6 and run `/harness-review WHI-xxx`."
- **Alternative (if Agent tool supports model hints):** Dispatch an Opus subagent with the complete diff + issue spec + review history. The subagent reviews and reports back.

**`/harness-dev` ends here.** Step 7 (final review + close) is handled by `/harness-review` below.

**Output:** Issue implemented, reviewed, committed, moved to "In Review", Linear comment posted with review summary

## Skill 4: `/harness-review`

**Purpose:** Opus-level final review of an implemented issue. Intended to be invoked with Opus 4.6 after `/harness-dev` completes.

**Input:** Linear issue ID (e.g., WHI-123)

**Preconditions:**
- Issue must be in "In Review" state
- A worktree with the implementation must exist (the feature branch)
- The issue's Linear comments should include the review summary from `/harness-dev` Step 6

**Workflow:**
1. Read the Linear issue via MCP. Verify state is "In Review".
2. Read the most recent Linear comment (the review summary from harness-dev).
3. Read CLAUDE.md for project context.
4. Recover the feature branch name: run `git worktree list` and filter for branches containing the issue ID (e.g., `WHI-123`). If no matching worktree found, check Linear comments for the branch name (harness-dev Step 6 includes it in the review summary comment).
5. Get the full diff: `git diff dev...<feature-branch>` from the main repo root (not inside the worktree).
5. Review the complete diff against the original issue spec:
   - Classify each acceptance criterion as: Met / Partially Met / Not Met
   - For statically verifiable criteria: check the code directly
   - For runtime-only criteria (performance, UX): flag as "requires manual verification" with suggested test approach
   - Check for: edge cases, error handling, test coverage, code quality
6. **If all criteria Met:**
   - Switch to the main repo root (not the worktree): `cd <project-root>`
   - Merge feature branch to dev: `git checkout dev && git merge --no-ff <branch>`
   - Remove worktree: `git worktree remove .worktrees/<name>`
   - Delete feature branch: `git branch -d <branch>`
   - Move Linear issue to "Done"
   - Output: "WHI-xxx development complete, review passed"
   - Note: the merge MUST happen from the main repo working directory, not from inside the worktree. `git checkout dev` inside a worktree fails because the worktree IS the feature branch.
7. **If any criteria Not Met:**
   - Add a Linear comment with specific failures (file:line references)
   - Keep issue in "In Review"
   - Output failures and flag for human decision (fix manually or re-invoke harness-dev)

**Output:** Issue either moved to Done (merge + cleanup) or kept in In Review with specific feedback

**Model requirement:** This skill should be invoked with Opus 4.6 for highest review quality. It will work with any model but the review depth depends on model capability.

### State Machine

```
Backlog/Todo ──[Step 2]──► In Progress ──[Step 6]──► In Review ──[/harness-review]──► Done
                                │                         │
                                │ (fix loop fails)        │ (Opus rejects)
                                └─── stays In Progress    └─── stays In Review
```

Steps 3, 4, and 5 all execute while the issue is in "In Progress" state. The Linear state only changes at Step 2 (entry) and Step 6 (handoff). The initial adversarial review (Step 4) does NOT count toward the 2-iteration fix loop cap.

The skill accepts issues in Backlog OR Todo state. It transitions directly to In Progress (the Todo → In Progress transition is implicit — the skill doesn't require the issue to be in Todo first).

### Worktree Lifecycle

```
Created:  Step 2 (git worktree add .worktrees/<name> -b <branch> dev)
Used:     Steps 3-6 (all implementation, fixes, and review handoff happen here)
Cleanup:  
  - On success (/harness-review Done): merge to dev, remove worktree, delete branch (done by /harness-review)
  - On human review flag (Step 5 or /harness-review reject): worktree PRESERVED for human to inspect
  - On error/crash: worktree PRESERVED, Linear issue stays In Progress
```

The skill never silently deletes a worktree that has uncommitted changes.

### Re-invocation Behavior

If the user re-invokes `/harness-dev WHI-123` on an issue that already has an in-progress worktree:

1. Check `git worktree list` for a branch matching `*/WHI-123-*`
2. If found:
   - Skip Step 1 (re-run quality gate as safeguard, but don't block if it passed before)
   - Skip Step 2 (worktree already exists, Linear already In Progress)
   - Check if the worktree has uncommitted changes: if yes, ask user "Resume with existing changes or start fresh?"
   - Resume from Step 3 (implementation) using the existing worktree
3. If not found: run the full workflow from Step 1

### Error Recovery

If the skill fails at any step:
- **Step 1 (quality gate):** No cleanup needed. Issue stays in original state.
- **Step 2 (after Linear state change but before worktree):** Roll back Linear state to previous value via MCP.
- **Step 3-5 (during implementation):** Worktree preserved. Linear stays In Progress. User can re-invoke to retry (see Re-invocation Behavior above).
- **Step 6 (during handoff):** Issue in In Review. Worktree preserved. User runs /harness-review or decides manually.

### Branch Type Inference

| Signal | Type |
|--------|------|
| Linear label "Bug" OR title contains "fix" or "bug" | `fix` |
| Linear label "Chore" or "Maintenance" OR title contains "chore" or "refactor" | `chore` |
| Everything else (default) | `feat` |

### Model Routing Summary

| Step | Model | Mechanism |
|------|-------|-----------|
| Quality Gate | Whatever user invoked with | Direct execution |
| Implementation | Whatever user invoked with (recommend Sonnet) | Direct execution |
| Adversarial Review | Multi-model | Delegated to /adversarial-review:run |
| Fix Loop | Whatever user invoked with | Direct execution |
| Final Review | Opus 4.6 | Separate skill (/harness-review) or subagent |

## Success Criteria

- A single invocation of `/harness-dev WHI-123` takes an issue from Backlog/Todo to In Review without manual prompt writing
- `/harness-review WHI-123` (invoked with Opus) takes an issue from In Review to Done
- Issue quality gate catches missing schema sections before wasting implementation time
- The full dev loop (impl → review → fix → review handoff) runs with appropriate model delegation
- Linear state transitions happen automatically at each step boundary
- Worktree is created, used, and cleaned up automatically (preserved on failure for inspection)
- The workflow is project-agnostic — works on TypeScript, Python, or any other stack
- Time savings: ~30 minutes of manual prompt writing per issue eliminated
- Adversarial review findings are classified by severity, preventing over-correction on style issues

## Build Order

1. **Define the shared issue schema** — this is the contract everything else depends on. Derive it from real forkcast-cli issues (see Assignment below).
2. **Build `/harness-dev`** — the repeating loop, highest frequency use. This also validates the schema in practice (the quality gate tests whether the schema actually predicts implementation success).
3. **Build `/harness-review`** — the Opus final review step, small skill. Needed to complete the harness-dev workflow.
4. **Build `/harness-design`** — the design-to-issues pipeline. Built AFTER harness-dev so the schema has been validated by real usage. The design skill produces issues that pass harness-dev's quality gate.
5. **Build `/harness-bootstrap`** — needed for new projects, references the schema. Lowest priority because it's a one-time-per-project setup.

Note: Steps 2 and 4 are co-dependent (premise 1). The resolution: build harness-dev first to validate the schema, then build harness-design to produce issues that conform to the validated schema. If the schema needs revision after harness-dev testing, update both.
